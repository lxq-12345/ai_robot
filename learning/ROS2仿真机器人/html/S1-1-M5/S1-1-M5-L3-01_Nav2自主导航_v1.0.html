S1-1-M5-L3-01 Nav2自主导航¶

所属开发单元：S1-1-M5 SLAM、定位与Nav2
所属学习子单元：S1-1-M5-L3 Nav2自主导航
章节序号：S1-1-M5-L3-01
教材版本：v1.0
涉及组件：Nav2、AMCL、地图服务器、Gazebo、cmd_vel_guard
安全边界：通过Nav2 Action或项目人工体验入口下达目标；不直接发布速度Topic。

1. 学习目标¶

理解Nav2生命周期、NavigateToPose Action、全局规划、局部控制、代价地图、行为树、取消、恢复、动态障碍和扫描超时安全。导航成功不仅是“机器人动了”，还要求目标状态、路径、安全速度链和清理都正确。

2. 导航链路¶

目标位姿
→ bt_navigator
→ planner_server / global costmap
→ controller_server / local costmap
→ velocity_smoother
→ /cmd_vel_raw
→ cmd_vel_guard
→ /cmd_vel
→ Gazebo底盘
→ /odom、TF、/scan反馈

nav2_bringup.launch.py先建立定位，再包含Nav2 bringup，并把Nav2的/cmd_vel重映射到/cmd_vel_raw。安全守卫是所有速度命令进入底盘前的统一边界。

3. 生命周期与Action¶

地图、定位和Nav2服务器必须进入Active后才提供完整能力。Action包含目标接受、反馈、取消和最终状态；“请求已发送”不等于目标已接受，“目标已接受”也不等于成功到达。

全局规划绕开静态障碍，局部控制根据实时扫描和代价地图生成速度；行为树协调规划、控制、清图和恢复。目标在障碍物内时应产生可解释结果，而不是无界等待。

4. 自动测试与人工入口¶

cd /home/ubuntu/ai_robot_ws
./scripts/build.sh
source install/setup.bash
launch_test tests/integration/test_s1_m5_nav2.launch.py
launch_test tests/integration/test_s1_m5_temporary_obstacle.launch.py
launch_test tests/integration/test_s1_m5_scan_timeout.launch.py

人工体验按tests/scenario/S1-1-M5-M6人工体验验收.md和scripts/start_m5_m6_manual_experience.sh执行。它通过Action下达目标，支持取消和观察安全停车，不直接发布速度命令。

5. 正常现象与安全场景¶

  • 所有关键生命周期节点进入Active；
  • 可达目标被接受并最终SUCCEEDED；
  • 全局路径绕开静态障碍；
  • 取消目标最终为CANCELED并停止；
  • 临时障碍进入雷达和局部代价地图，移除后清除；
  • 扫描陈旧时守卫发布零速度并阻止继续运动；
  • /cmd_vel不超过项目线速度和角速度上限。

6. 常见问题与停止¶

  • Action不可用：查生命周期和命名；
  • 目标拒绝或超时：查地图、定位、服务器状态；
  • 有路径不运动：查控制器、局部代价地图和速度链；
  • 原地振荡：查目标容差、障碍膨胀和DWB轨迹；
  • 障碍不响应：查/scan、Frame和local costmap；
  • 取消后仍动：立即判定安全失败，查Action状态和守卫输出。

人工场景异常时先使用其安全停止步骤，再Ctrl+C退出启动器；确认Gazebo、Nav2、任务管理器和速度守卫退出。

7. 实体迁移与证据¶

实体阶段保持NavigateToPose语义和安全速度链，但地图、定位、足迹、加速度、代价地图、控制器和恢复策略必须现场调参与验收。证据记录目标、路径、Action状态、障碍响应、速度限制、停止和日志。

8. 理解检查¶

  1. 为什么Nav2速度必须重映射到/cmd_vel_raw？
  2. Lifecycle Active与Action server可见有什么关系？
  3. 全局规划和局部控制分别处理什么？
  4. 取消成功后还需要观察什么？
  5. 扫描超时为什么必须在安全守卫处形成零速度？
