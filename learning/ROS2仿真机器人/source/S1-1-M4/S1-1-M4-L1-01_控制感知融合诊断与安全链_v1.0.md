## 1. 学习目标

理解M2底盘和M3传感器如何组成控制、感知、诊断、状态估计和安全子系统。学员应能沿Topic、TF、参数和节点定位“数据在哪一段丢失或变坏”。

## 2. 五条集成链

1. 控制链：`/cmd_vel_raw -> cmd_vel_guard -> /cmd_vel -> Gazebo`；
2. 反馈链：轮状态与Gazebo里程计形成`/joint_states`、`/odom`和`odom -> base_link`；
3. 感知链：`/scan`进入`scan_obstacle_monitor`，图像与CameraInfo进入`camera_image_monitor`；
4. 诊断链：监测节点向`/diagnostics`发布状态和关键值；
5. 融合链：`/odom + /imu/data -> ekf_filter_node -> /odometry/filtered`。

安全链横跨以上对象：命令超时、可选扫描新鲜度、限速和零速度输出必须在下游执行前生效。

## 3. TF与融合责任

`config/ekf_sim.yaml`使用二维模式、30 Hz、0.2 s传感器超时，融合`/odom`与`/imu/data`。当前Gazebo拥有`odom -> base_link`，因此EKF设置`publish_tf: false`，避免同一TF重复发布。`/odometry/filtered`仍应使用`odom`和`base_link`作为Frame。

融合不是“让所有传感器都更准确”，而是按配置选择状态变量和不确定性。输入时间戳、Frame或协方差错误都会污染输出。

## 4. 感知与诊断节点

`scan_obstacle_monitor`从有效雷达范围取最近障碍距离，发布`s1_m4.scan_obstacle`诊断；`camera_image_monitor`比较图像与CameraInfo，发布`s1_m4.camera_image_chain`。诊断OK/WARN/ERROR表达链路状态，不替代原始数据。

第三方依赖状态由`config/s1_m4_dependency_status.yaml`记录。成熟组件上游内部测试不复制，本项目验证版本可用、配置正确、输入输出和退出行为符合契约。

## 6. 正常现象与首查位置

- 诊断正常：Frame和值字段与原始消息一致；
- EKF正常：持续发布有限值，Frame为`odom/base_link`；
- 重复TF警告：查`publish_tf`和Gazebo插件；
- 诊断无输出：查监测节点、订阅和QoS；
- EKF不输出：查输入时间戳、Frame、配置数组和依赖；
- 安全停车异常：从守卫输入、扫描新鲜度、定时器和输出逐段检查。

## 7. 安全停止、实体迁移与证据

异常时停止测试Launch并确认所有节点退出，不临时关闭安全断言。实体阶段保留上层Topic和诊断语义，但需替换驱动、重建协方差、标定时间偏移并增加硬件安全链。证据记录链路图、配置解释、局部测试、观察和首查路径。

## 8. 理解检查

1. 为什么当前EKF不发布TF？
2. `/diagnostics`与原始传感器Topic是什么关系？
3. 传感器Topic存在但诊断ERROR时应查什么？
4. 成熟第三方组件为什么仍需项目集成测试？
5. 安全链为什么不能只在Nav2内部实现？
