## 排查过程

- Codex日志曾出现以下相关线索：

  - `Failed to release queued message send lock`；
  - 多项`fs/getMetadata`文件不存在错误。
- 上述日志说明队列通知、发送锁和本地文件元数据路径存在异常线索，但不能单独证明具体根因。
- 公开资料中存在相似报告：

## 实际解决过程（本机已验证）

1. 保留原会话和排队问题证据，不删除`.codex`目录、不清空会话、不修改Codex扩展源码。
2. 用户重新加载VS Code窗口，使旧Codex扩展宿主和旧app-server结束，并重新初始化Codex侧栏。
3. 重新加载后，Codex扩展在`2026-10-03 18:49:49 PDT`重新激活并创建新的app-server。后续只读核对确认：
   - VS Code扩展登记路径为`openai.chatgpt-26.917.62051`；
   - 实际运行的app-server路径同为`openai.chatgpt-26.917.62051/bin/linux-x86_64/codex`；
   - `codex-code-mode-host`也来自相同版本目录。
4. 这次重新加载消除了故障前“登记版本`26.930.31730`、运行进程`26.930.31428`”的不一致状态，并重建了app-server、会话所有权和队列协调状态。日志在启动阶段仍尝试释放旧队列发送锁并给出警告，但新会话执行链随后可继续工作。
5. 用户在恢复后的同一会话连续提交五条“测试提问”；每条均收到回答，没有消息继续停留在队列。
6. 日志从`18:51:17 PDT`开始为该会话连续记录新的`turn-start`，证明消息已经越过输入框、排队和发送锁阶段，进入后台执行。

本次可复用的实际解决办法是：**重新加载VS Code，使扩展登记版本与实际运行的Codex后台版本一致，并重建app-server和队列状态；随后用连续提问及`turn-start`日志确认恢复。**本机这次恢复后生效的版本为`26.917.62051`。现有证据不能证明必须固定使用该版本，也不能证明单独重载在所有复发场景中都有效。

## 恢复与验证结果

- 用户重新加载VS Code后，扩展登记版本和实际app-server均为`26.917.62051`，不再保持故障排查阶段的版本错配。
- 连续五条“测试提问”均正常送达并获得响应。
- 扩展日志在同一会话中记录了对应的新`turn-start`事件，说明这些消息已进入后台执行。
- 五次恢复测试期间未新增`Failed to release queued message send lock`警告；重新加载初期存在较早的队列锁释放失败记录。
- 当前结论：通过“重新加载VS Code、统一实际加载版本、重建app-server和队列状态”恢复了队列功能，本轮连续测试未复现阻塞。版本错配与阻塞之间的唯一因果关系尚未严格证明，不能据此宣称扩展缺陷已永久修复。
