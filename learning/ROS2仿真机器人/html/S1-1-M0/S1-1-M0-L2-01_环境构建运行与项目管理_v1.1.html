S1-1-M0-L2-01 环境、构建、运行与项目管理¶

所属开发单元：S1-1-M0 工程与管理基线
所属学习子单元：S1-1-M0-L2 环境、构建、运行与项目管理
章节序号：S1-1-M0-L2-01
教材版本：v1.1
适用项目：/home/ubuntu/ai_robot_ws
适用环境：Ubuntu 22.04、ROS 2 Humble、colcon、Git
学习边界：只运行环境检查、构建、非运动示例节点和Git只读观察；不执行实体机器人操作，不启动AI Agent，不把本章练习记作M0-L3测试结论。

1. 本章要解决什么问题¶

拥有ROS 2源码并不等于当前终端能够运行它。一个可重复的工作过程至少要回答：

  1. 当前Shell是否加载了正确的ROS 2发行版；
  2. colcon从哪里读取源码，又把结果写到哪里；
  3. 为什么构建成功后仍可能找不到项目程序包；
  4. 如何运行一个不会驱动机器人的示例节点并正常停止；
  5. 标准测试入口在构建流程中的位置；
  6. 如何用Git判断当前文件、提交和远端是否一致；
  7. 哪些输出是工程结果，哪些只是临时生成物或聊天结论。

本章学习的是工程操作链路，不深入测试断言。M0-L3将单独学习工程基线测试与证据。

2. 学习目标和完成边界¶

完成讲解和正式练习后，学员应能够：

  • 解释系统ROS 2环境与项目安装环境的先后关系；
  • 使用项目脚本检查环境并读懂成功、失败和退出码；
  • 解释src/、build/、install/和log/在构建链中的关系；
  • 使用统一脚本完成增量构建；
  • 在新终端中正确加载项目安装空间；
  • 运行、观察并停止一个不产生机器人运动的示例节点；
  • 说明scripts/test.sh为什么必须在构建之后运行；
  • 使用只读Git命令判断分支、工作区、最近提交和远端配置；
  • 说明本地提交、推送和远端核验为什么是三个不同状态。

本章完成不表示M0学习结项。M0-L3测试与证据未完成前，M0学习状态仍不能标记为完成。

3. ROS 2环境是分层加载的¶

3.1 系统ROS 2是Underlay¶

ROS 2 Humble安装在：

/opt/ros/humble/

加载系统环境：

source /opt/ros/humble/setup.bash

这一步让当前Shell获得ROS 2命令、系统程序包、Python模块、共享库和索引路径。可以观察：

echo "$ROS_DISTRO"
command -v ros2
command -v colcon

本项目预期ROS_DISTRO为humble。

3.2 项目安装空间是Overlay¶

项目构建成功后生成：

/home/ubuntu/ai_robot_ws/install/setup.bash

加载项目环境：

source /home/ubuntu/ai_robot_ws/install/setup.bash

Overlay把本项目程序包叠加到系统ROS 2之上。正确顺序是：

系统ROS 2 Humble setup
        ↓
项目install/setup.bash
        ↓
ros2 run、ros2 launch和测试发现项目程序包

项目的install/setup.bash通常会保留构建时的Underlay关系，但显式先加载系统环境更容易理解和排错。

3.3 source只影响当前Shell¶

在终端A执行source，不会自动改变终端B。新开终端后如果出现“package not found”，首先确认该终端是否加载了项目安装空间。

source也不会永久修改源码或程序包。它只改变当前进程及其子进程的环境变量。

4. 环境检查入口¶

项目环境检查入口是：

./scripts/check_environment.sh

脚本执行以下检查：

  1. /opt/ros/humble/setup.bash存在；
  2. 加载ROS 2 Humble环境；
  3. colcon、ros2、rviz2、gazebo和gzserver命令可定位；
  4. src/、config/、scripts/、tests/和resources/目录存在；
  5. 输出ROS 2发行版和工作空间路径。

当前正常输出的核心形式是：

ROS_DISTRO=humble
Workspace baseline check passed: /home/ubuntu/ai_robot_ws

脚本使用set -euo pipefail。这意味着未处理的命令失败、未定义变量或管道失败会使脚本返回非零退出码。成功文本不能取代退出码，但在交互终端中两者应一致。

只读环境检查不会构建程序包，也不会启动机器人节点。

5. colcon构建链¶

5.1 四个空间¶

src/       权威源码和程序包资源
  │
  │ colcon build
  ▼
build/     编译、生成和中间产物
  │
  ▼
install/   可供ROS 2发现和运行的安装结果

log/       构建与测试过程日志

build/、install/和log/是生成空间，不作为长期源码编辑位置，也不提交Git。

5.2 项目构建入口¶

标准命令是：

./scripts/build.sh

脚本把colcon路径固定为：

--base-paths   /home/ubuntu/ai_robot_ws/src
--build-base   /home/ubuntu/ai_robot_ws/build
--install-base /home/ubuntu/ai_robot_ws/install
--log-base     /home/ubuntu/ai_robot_ws/log

因此无论脚本从哪个目录被调用，项目根路径都由脚本自身计算。不过课程练习统一从项目根目录执行，便于观察和记录。

5.3 增量构建与重新加载¶

colcon默认复用已有构建结果。源码变化后再次运行./scripts/build.sh通常是增量构建。

构建成功后，已经打开的终端仍可能保留旧环境。稳妥顺序是：

./scripts/build.sh
source install/setup.bash

新终端则重新执行系统环境和项目环境加载。

不要为了“彻底一点”随意删除build/、install/和log/。清理构建会增加耗时，也可能掩盖应当定位的依赖或配置问题；只有明确需要干净构建时才按项目任务处理。

5.4 怎样读构建结果¶

重点观察：

  • 哪些程序包被发现；
  • 哪个程序包首先出现stderr或Failed；
  • 最终Summary中成功、失败和中止数量；
  • 命令退出码是否为0；
  • log/latest_build/中的对应日志。

后续程序包的失败可能是前序依赖失败造成的。排错时先处理第一个真实失败，而不是只看最后一行。

6. 加载并确认项目程序包¶

构建并加载Overlay后，可以执行：

ros2 pkg prefix ai_robot_py_example
ros2 pkg executables ai_robot_py_example
ros2 pkg prefix ai_robot_sim

正常情况下，ros2 pkg prefix指向工作空间install/中的对应程序包，而不是src/。

如果colcon list能看到程序包但ros2 pkg prefix看不到，通常说明“源码发现”已经成功，但“安装空间未构建或当前Shell未加载”。这是两个不同阶段。

7. 安全的运行与观察¶

本章只运行不产生底盘运动的Python示例节点。

终端1：

cd /home/ubuntu/ai_robot_ws
source /opt/ros/humble/setup.bash
source install/setup.bash
ros2 run ai_robot_py_example baseline_node

预期日志包含：

ai_robot_py_example:ready

保持终端1运行，在终端2执行：

cd /home/ubuntu/ai_robot_ws
source /opt/ros/humble/setup.bash
source install/setup.bash
ros2 node list
ros2 node info /baseline_py_node

预期能够看到/baseline_py_node。观察完成后回到终端1按Ctrl+C，确认节点正常退出。

本章禁止启动运动演示、直接发布/cmd_vel或/cmd_vel_raw。即使当前是仿真学习，也不能把与本章无关的运动命令混入工程基线练习。

8. 标准测试入口在什么位置¶

标准全量测试入口是：

./scripts/test.sh

它按以下顺序执行：

工作空间目录契约
→ 加载已构建的install空间
→ 所有程序包注册测试
→ 公共契约测试
→ M1至M6跨包集成测试
→ M6系统测试

测试脚本要求install/setup.bash已经存在；没有构建时会提示先运行./scripts/build.sh。ROS测试日志统一写入项目log/test/。

本章只理解入口、顺序和前置条件。正式阅读测试注册、执行基线测试、解释断言并记录证据属于M0-L3。不要把AI此前执行的全量回归直接记为自己的M0-L3学习证据。

9. Git项目状态观察¶

9.1 工作区和分支¶

git status --short --branch
git branch --show-current

git status --short --branch同时显示当前分支、上游关系和文件变化。没有文件条目表示工作区没有未提交变化，但不自动表示本地已经推送远端。

9.2 最近提交和上游¶

git log -1 --oneline
git branch -vv
git remote -v

这些命令分别回答：

  • 当前HEAD是什么提交；
  • 当前分支跟踪哪个上游，是否领先或落后；
  • origin指向哪个远端仓库。

9.3 三种归档状态¶

工作区干净
≠ 已创建本地提交
≠ 已推送并核验远端

项目里程碑归档顺序是：

测试与安全检查
→ 更新状态和备忘
→ 本地提交
→ 推送origin
→ 读取远端提交号
→ 确认本地不领先上游

本章练习只做Git只读观察，不创建提交、不修改远端。教材和项目文件的实际归档由当前任务流程统一完成。

10. 正式练习¶

以下步骤必须由学员亲自执行。AI此前运行相同命令只算技术验证，不算正式练习。

10.1 环境检查¶

cd /home/ubuntu/ai_robot_ws
pwd
./scripts/check_environment.sh
echo "$ROS_DISTRO"
command -v ros2
command -v colcon

记录环境检查是否通过、ROS 2发行版以及ros2、colcon的实际路径。

10.2 构建与安装空间¶

./scripts/build.sh
source install/setup.bash
ros2 pkg prefix ai_robot_py_example
ros2 pkg executables ai_robot_py_example

记录构建Summary、安装前缀和可执行入口。

10.3 非运动节点运行¶

按第7节使用两个终端启动并观察baseline_node。记录节点名称、关键日志和Ctrl+C退出结果。

10.4 Git只读观察¶

git status --short --branch
git branch --show-current
git log -1 --oneline
git branch -vv
git remote -v

记录当前分支、最近提交、上游分支、是否领先或落后，以及工作区是否存在非预期变化。

10.5 练习结论¶

练习完成后回答：

  1. 系统ROS 2和项目Overlay分别提供什么；
  2. 为什么构建成功后还要加载install/setup.bash；
  3. colcon list可见但ros2 pkg prefix不可见说明问题可能在哪一层；
  4. 构建失败时为什么先找第一个失败程序包；
  5. 工作区干净为什么不等于远端归档完成。

11. 常见问题与首查位置¶

11.1 ROS_DISTRO为空¶

当前Shell没有加载系统ROS 2。执行source /opt/ros/humble/setup.bash，再重新检查。

11.2 install/setup.bash不存在¶

工作空间尚未成功构建。先执行./scripts/build.sh，并处理第一个构建失败。

11.3 ros2 run提示package或executable不存在¶

依次检查构建Summary、install/setup.bash、当前Shell环境、ros2 pkg prefix和程序包安装规则。

11.4 运行行为像旧版本¶

确认修改发生在src/或config/权威源，重新构建，并在当前Shell重新加载install/setup.bash。不要直接修补install/副本。

11.5 测试找不到项目可执行程序¶

确认先构建并加载安装空间。项目标准scripts/test.sh已经处理这一顺序，单独拼命令时容易遗漏。

11.6 Git显示非预期修改¶

停止后续写操作，先用git status --short和git diff确认来源。不得用重置或覆盖命令清除自己不了解的修改。

12. 停止、恢复与安全边界¶

  • 普通示例节点使用Ctrl+C停止；
  • 若命令长时间无输出，先确认它是常驻节点还是实际卡住；
  • 不使用kill -9作为默认停止方式；
  • 不直接操作.git/、build/或install/内部文件；
  • 不运行实体机器人驱动，不上电，不发布运动命令；
  • 不启动AI Agent或阶段2组件；
  • 发现环境、规划和实际入口不一致时，先修正规则或记录冲突，不靠临时命令绕过。

13. 对实体迁移的意义¶

实体机器人仍需要同样的环境、构建、Overlay和Git归档纪律，但实体阶段还会增加驱动依赖、设备权限、实时诊断和现场安全授权。

本章的命令不能自动获得实体操作权限。即使软件构建和测试通过，实体上电与运动仍必须由用户当次明确授权，并满足S1-1-G1和后续实体阶段准入条件。

14. 本章总结¶

  1. ROS 2运行环境由系统Underlay和项目Overlay分层组成；
  2. source只影响当前Shell，新终端需要重新加载；
  3. ./scripts/check_environment.sh验证系统命令和工作空间基线；
  4. ./scripts/build.sh把src/构建为build/和install/，日志写入log/；
  5. ROS 2运行项目程序包依赖已经构建并加载的install/setup.bash；
  6. 本章只运行非运动示例节点，观察后使用Ctrl+C正常退出；
  7. ./scripts/test.sh是统一回归入口，测试与证据学习留到M0-L3；
  8. Git工作区、本地提交和远端归档是三个不同层次。

15. 理解检查¶

请在正式练习前先用自己的话回答：

  1. Underlay和Overlay分别是什么？加载顺序为什么重要？
  2. 为什么终端A加载工作空间后，终端B仍可能找不到项目包？
  3. src/、build/、install/和log/如何形成构建链？
  4. 环境检查通过能否证明所有机器人功能测试通过？为什么？
  5. scripts/test.sh为什么检查install/setup.bash？
  6. 本章为什么选择ai_robot_py_example/baseline_node而不选择底盘运动演示？
  7. 如何只读判断本地分支是否跟踪origin/main？
  8. 为什么“工作区干净”不能作为远端归档完成证据？

理解检查完成并由AI教员讲解确认后，再执行第10节正式练习。练习完成后进入M0-L3工程基线测试与证据，不直接跳到M1。
