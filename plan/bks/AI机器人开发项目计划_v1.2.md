# AI机器人开发项目计划 v1.2

> 文档定位：AI机器人项目的实施基线。  
> 当前范围：室内差速轮式移动机器人，不含机械臂。  
> 技术基线：Ubuntu 22.04、ROS 2 Humble、VS Code + Codex；Claude可用于辅助审查。  
> 总体顺序：先完成ROS 2机器人部分，再开发AI Agent部分。  
> 规划原则：机器人先行；先模拟、后实体；成熟资源优先；接口先行；对象化封装；分层测试；阶段门控制。

## 1. 项目目标

在Ubuntu服务器上建立一套可持续开发、测试、迁移和维护的AI机器人系统。项目先形成不依赖大模型也能独立运行的ROS 2机器人，再在其稳定能力接口之上开发AI Agent，最终实现：

```text
用户输入文字、语音、图片或视频
→ AI大模型理解任务并进行高层规划
→ AI—ROS 2接口生成受约束的物理任务
→ ROS 2完成感知、定位、导航和运动控制
→ 驱动、MCU和机器人本体执行动作
→ 系统返回任务进度、结果和异常
```

首个综合验收场景：

> 用户下达“去客厅门口看看有没有人”的任务，机器人能够解析地点、取得经过确认的目标位姿、自主导航、到点检测人员并反馈结果；遇到无效地点、定位失败、通信中断或急停时，能够拒绝任务或安全停车。

## 2. 总体实施结构

项目采用“一项公共基础、两部分开发规划、两个阶段准入门、三条贯穿主线”。

```text
公共工程基线
    ↓
第一部分：ROS 2机器人开发规划
    ├── 模拟机器人开发
    ├── G1：仿真到实体准入门
    ├── 实际机器人开发
    └── G2：ROS 2机器人能力验收
    ↓
第二部分：AI Agent开发规划
    ├── AI Agent架构与任务协议
    ├── AI大模型层
    ├── AI—ROS 2接口层
    ├── 仿真回归联调
    └── 实体机器人联调
    ↓
整体系统稳定化与发布
```

两部分的范围与先后关系：

| 开发部分 | 包含层级 | 核心目标 | 启动条件 |
|---|---|---|---|
| ROS 2机器人部分 | ROS 2机器人软件层；机器人硬件驱动与本体层 | 形成可独立感知、建图、定位、导航、避障和安全停车的机器人 | 公共工程基线完成 |
| AI Agent部分 | AI大模型层；AI—ROS 2接口层 | 将自然语言及多模态任务转换为受约束的机器人能力调用 | ROS 2机器人通过G2验收 |

用户交互层是系统入口，不单独构成开发部分；研发与验证体系贯穿两个部分。

三条贯穿主线：

1. **成熟资源主线**：调研、选型、验证、封装、版本冻结和升级管理；
2. **模块开发主线**：独立对象、子系统、整机ROS 2系统、AI机器人系统；
3. **测试主线**：单元测试、节点测试、接口契约测试、集成测试、系统测试和端到端验收。

项目同时采用两种推进方向：

```text
自底向上：
设备/算法对象 → ROS 2节点 → 子系统 → ROS 2整机 → AI机器人系统

自顶向下：
用户任务 → 结构化任务 → 模拟接口/测试桩 → 逐步替换为仿真或实体节点
```

在ROS 2机器人部分，自底向上是主要实施路线，自顶向下用于从“导航到目标、观察环境”等机器人能力场景反推接口和验收要求。在AI Agent部分，自顶向下从用户任务出发，并使用测试桩、仿真机器人和实体机器人逐级联调。

### 2.1 两部分之间的依赖边界

ROS 2机器人部分先提供稳定的“能力服务”，例如：

```text
获取机器人状态
导航到指定位姿
取消导航
检测人员
返回充电点
进入安全停车状态
```

AI Agent只能通过冻结后的Topic、Service、Action及自定义任务接口调用这些能力。ROS 2机器人在没有AI Agent的情况下，也必须能够通过CLI、RViz2、测试程序或普通控制界面独立完成验收。

## 3. 系统分层与职责

| 归属 | 层级 | 主要职责 | 边界 |
|---|---|---|---|
| 系统入口 | 用户交互层 | 接收文字、语音、图片、视频，展示结果 | 不直接控制机器人 |
| AI Agent部分 | AI大模型层 | 多模态理解、任务理解、高层任务规划 | 不直接发布速度命令，不凭空决定物理坐标 |
| AI Agent部分 | AI—ROS 2接口层 | 结构化任务、语义目标物理化、合法性校验、能力调用 | 不替代Nav2、控制器和硬件安全 |
| ROS 2机器人部分 | ROS 2机器人软件层 | 任务调度、感知、SLAM、定位、Nav2、运动与安全控制 | 不承担电机底层实时闭环 |
| ROS 2机器人部分 | 硬件驱动与本体层 | 底盘和传感器驱动、MCU通信、电机闭环、硬件安全 | 不理解自然语言 |
| 贯穿体系 | 研发与验证体系 | VS Code、Codex/Claude、Git、构建、仿真、测试、文档 | 不进入机器人运行时控制链 |

大模型只能调用经过白名单控制的机器人能力，例如：

```text
get_robot_status()
navigate_to(location)
detect_person()
cancel_task()
return_to_home()
```

禁止大模型直接控制电机、持续发布`/cmd_vel`、任意执行Shell命令或绕过安全节点。

## 4. 成熟ROS 2资源的获取与使用

### 4.1 基本策略

项目不从零重写ROS 2已有的通用能力，采用以下顺序：

```text
明确对象和接口
→ 调研成熟资源
→ 核对ROS 2 Humble及Ubuntu 22.04兼容性
→ 建立最小验证样例
→ 完成独立节点与接口测试
→ 项目封装和配置
→ 纳入子系统集成
→ 冻结版本及记录来源
```

成熟程序解决“通用能力”，本项目负责：

- 选型及兼容性验证；
- 参数、Topic、Frame和QoS适配；
- 启动文件和配置管理；
- 项目统一接口封装；
- 与其他节点联调；
- 实体硬件协议、标定和安全；
- AI—ROS 2任务协议及业务逻辑。

### 4.2 初始资源候选清单

| 对象能力 | 优先考察的成熟资源 | 项目工作 |
|---|---|---|
| 机器人模型 | URDF、Xacro、`robot_state_publisher` | 建立本机尺寸、关节和传感器安装模型 |
| 差速底盘控制 | `ros2_control`、`diff_drive_controller` | 配置轮径、轮距和限制；开发实体硬件接口 |
| 仿真平台 | Gazebo及ROS 2桥接/控制插件 | 建立机器人模型、世界、传感器和故障场景 |
| 激光雷达 | 具体品牌的官方或主流ROS 2驱动 | 验证型号、数据频率、QoS、Frame和`LaserScan` |
| 相机 | USB Camera、RealSense、Orbbec等对应驱动 | 验证图像、相机参数、帧率和时间戳 |
| 图像处理 | `image_pipeline`、`image_transport` | 校正、压缩、格式及传输配置 |
| IMU/里程计融合 | `robot_localization` | 建立EKF配置、协方差和坐标约定 |
| 坐标变换 | `tf2`、`robot_state_publisher` | 设计并持续验证TF树 |
| SLAM | `slam_toolbox` | 配置建图、地图保存和定位模式 |
| 定位和导航 | Nav2、AMCL | 配置规划器、控制器、代价地图和行为树 |
| 视觉识别 | OpenCV、YOLO及适用的ROS 2封装 | 选择模型并统一检测结果接口 |
| 数据记录 | `rosbag2` | 建立测试数据集、问题复现和回放测试 |
| 可视化诊断 | RViz2、`rqt`、ROS 2 CLI、diagnostics | 建立调试与验收视图 |

这只是候选清单，不等于最终选型。每个资源都必须通过本项目的“资源准入检查”。

### 4.3 资源准入检查

每个第三方资源建立一张资源卡，至少记录：

- 项目名称、来源和许可证；
- 维护状态、发行版和最近稳定版本；
- ROS 2 Humble及Ubuntu 22.04兼容性；
- 安装方式和依赖；
- 输入输出Topic、Service、Action及QoS；
- TF、时间戳和参数要求；
- CPU、GPU、内存及网络需求；
- 仿真实现和实体实现；
- 最小验证结果；
- 已知问题、替代方案和回退方式；
- 项目锁定的版本或提交号。

资源准入标准：

1. 来源可靠，许可证允许项目使用；
2. 能在项目基线环境构建或安装；
3. 最小样例可稳定启动和停止；
4. 接口能够适配项目统一约定；
5. 关键输出可自动检查；
6. 故障不会绕过安全控制；
7. 有版本记录和可重复安装方法。

对成熟第三方包，原则上不直接修改其源码。优先采用参数配置、适配节点或薄封装；确需修改时，应维护补丁原因、测试和上游版本对应关系。

## 5. 面向对象与模块化设计

### 5.1 对象划分

机器人能力划分为职责单一、接口稳定、可独立测试、可替换的对象：

| 对象 | 典型ROS 2实现 | 主要职责 |
|---|---|---|
| 底盘对象 | `BaseDriverNode` | 接收速度命令，发布里程计和设备状态 |
| 雷达对象 | 雷达驱动/适配节点 | 发布标准激光扫描数据 |
| 相机对象 | 相机驱动/适配节点 | 发布图像与相机参数 |
| IMU对象 | IMU驱动/适配节点 | 发布惯性数据及状态 |
| 定位对象 | 融合与定位节点 | 发布稳定的位姿和坐标变换 |
| 导航对象 | Nav2能力封装 | 接收目标、反馈进度、支持取消 |
| 感知对象 | `PerceptionNode` | 输出标准化目标检测结果 |
| 安全对象 | `SafetySupervisorNode` | 限速、超时、急停、命令仲裁 |
| 机器人任务对象 | `TaskManagerNode` | 执行非AI机器人能力状态机和异常处理 |
| AI桥接对象 | `AiRosBridgeNode` | 在G2之后开发，校验结构化任务并调用白名单能力 |

节点内部采用类封装状态和行为；算法、协议、任务规则尽量放入不依赖ROS 2的普通类，以便单元测试。

### 5.2 仿真与实体的统一接口

| 能力 | 仿真实现 | 实体实现 | 上层接口 |
|---|---|---|---|
| 底盘 | Gazebo/控制插件 | MCU和实体底盘驱动 | `/cmd_vel`、`/odom`、TF |
| 激光雷达 | 仿真雷达 | 实体雷达驱动 | `/scan` |
| 相机 | 仿真相机 | 实体相机驱动 | `/camera/*` |
| IMU | 仿真IMU | 实体IMU驱动 | `/imu/data` |
| 安全状态 | 故障注入节点 | 急停、电池和设备状态 | 统一安全/诊断接口 |

切换方式：

```text
mode:=sim   → 加载仿真驱动、仿真传感器和仿真参数
mode:=real  → 加载实体驱动、实体传感器和实机参数
```

机器人任务管理和能力接口不应感知底层是仿真还是真机；G2之后开发的AI桥接只依赖这些统一能力接口。

## 6. 测试体系

### 6.1 测试层级

| 级别 | 测试对象 | 主要方法 | 示例 |
|---|---|---|---|
| T1 代码单元测试 | 自研普通类和算法 | 白盒、无ROS或最小ROS依赖 | 协议编解码、任务校验、坐标转换、状态机 |
| T2 独立节点测试 | 单个自研或第三方节点 | 黑盒、接口契约、参数和生命周期测试 | 相机、雷达、底盘、IMU、AI桥接节点 |
| T3 子系统集成测试 | 多个相关节点 | Launch测试、录包回放、故障注入 | 底盘闭环、雷达+TF+SLAM、地图+定位+Nav2 |
| T4 ROS 2系统测试 | 完整机器人软件 | 仿真场景、重复运行和性能检查 | 建图、定位、导航、避障、安全停车 |
| T5 实体安全与机器人验收 | 真实机器人 | 架空、低速、限定区域、长稳测试 | 急停、失联停车、定位、导航和任务执行 |
| T6 AI端到端测试 | 用户任务到执行结果 | 测试桩、仿真、实体；正常、异常、边界和取消场景 | 导航到语义地点并检测人员 |

第三方成熟包通常不重复做其内部源码的白盒单元测试；项目应重点验证：

- 能否稳定启动、停止和重启；
- Topic、Service、Action和参数是否符合约定；
- 消息类型、频率、时间戳、QoS和Frame是否正确；
- 输入异常、传感器断开或数据超时时的表现；
- 与上下游节点组合后是否满足项目指标。

### 6.2 自底向上的测试链

```text
雷达/相机/IMU/底盘等独立节点
→ 运动、感知、定位、导航等子系统
→ ROS 2整机系统
→ AI机器人完整系统
```

典型子系统：

- 底盘控制＋编码器＋里程计＋TF；
- 雷达＋TF＋SLAM；
- IMU＋编码器＋`robot_localization`；
- 地图＋定位＋Nav2；
- 相机＋图像处理＋目标检测；
- 安全节点＋速度命令＋底盘控制；
- AI桥接＋任务管理＋Nav2 Action。

### 6.3 自顶向下的测试链

ROS 2机器人部分先从“建图、导航、感知、安全停车”等目标能力反推节点接口和系统场景。G2通过并进入AI Agent部分后，再通过测试桩、固定数据和模拟Action Server验证上层流程：

```text
用户任务
→ 大模型生成结构化任务
→ AI—ROS 2接口校验
→ 模拟Nav2返回到达
→ 模拟感知节点返回人员检测结果
→ 任务管理器生成最终反馈
```

AI Agent部分按顺序替换：

```text
测试桩
→ 仿真节点
→ 实体节点
```

这样既不提前把AI依赖引入ROS 2机器人开发，又能在AI Agent阶段尽早发现任务协议、状态机、取消机制和异常反馈方面的架构问题。

### 6.4 每个对象的“完成定义”

一个对象只有同时满足以下条件才算完成：

1. 职责和边界明确；
2. 成熟资源或自研方案已确定；
3. 接口、参数、QoS和TF有文档；
4. ROS 2机器人对象的仿真与实体替换关系明确；AI Agent对象与G2能力接口的依赖关系明确；
5. 自研代码单元测试通过；
6. 独立节点或接口契约测试通过；
7. 至少完成一个相关子系统集成测试；
8. 日志、诊断和异常行为可观察；
9. 版本、配置和测试证据已归档。

## 7. 里程碑总表

项目分为公共基础、ROS 2机器人开发、机器人能力验收、AI Agent开发和整体发布。

| 阶段 | 里程碑 | 主要目标 | 核心验收 |
|---|---|---|---|
| 公共基础 | M0 环境与工程基线 | 建立可重复的ROS 2研发环境 | 构建、测试、示例节点、RViz2和Gazebo正常 |
| 公共基础 | M1 资源、接口与测试基线 | 建立资源清单、对象边界和自动测试骨架 | 候选资源可追踪；公共接口及测试模板建立 |
| ROS 2机器人·模拟 | M2 仿真本体与底盘单元 | 建立URDF、差速底盘、里程计和TF | 独立运动、停车、里程计和TF测试通过 |
| ROS 2机器人·模拟 | M3 仿真传感器单元 | 分别接入雷达、相机和IMU | 每个传感器独立节点和接口测试通过 |
| ROS 2机器人·模拟 | M4 运动、感知与安全集成 | 形成底盘闭环、融合、感知和安全链 | 子系统集成、超时停车和故障注入通过 |
| ROS 2机器人·模拟 | M5 SLAM、定位与Nav2 | 完成建图、重定位、规划、控制和避障 | 重复导航场景达到冻结指标 |
| ROS 2机器人·模拟 | M6 仿真机器人综合验收 | 验证完整ROS 2机器人能力 | 不依赖AI即可完成导航、感知和异常处理 |
| 阶段门 | G1 仿真到实体准入 | 审查是否允许进入硬件开发 | 准入清单通过并冻结实体接口 |
| ROS 2机器人·实体 | M7 实体资源定型与安全准备 | 确定硬件、驱动、协议、安装和安全方案 | 硬件兼容性PoC、急停和测试方案通过 |
| ROS 2机器人·实体 | M8 实体设备单元测试 | 分别验证MCU、底盘、雷达、相机和IMU | 架空、独立、低速测试及接口契约通过 |
| ROS 2机器人·实体 | M9 实体运动、感知与安全集成 | 建立实机底盘、传感器、TF、融合和安全闭环 | 失联停车、标定和子系统集成通过 |
| ROS 2机器人·实体 | M10 实体SLAM、定位与Nav2 | 把仿真导航能力迁移到真实环境 | 限定区域多次导航和避障通过 |
| ROS 2机器人·实体 | M11 ROS 2机器人稳定化 | 形成可独立运行的实体机器人 | 长稳、恢复、部署和回归测试通过 |
| 阶段门 | G2 ROS 2机器人能力验收 | 审查是否允许开发AI Agent | 能力接口冻结；机器人可脱离AI独立验收 |
| AI Agent | M12 AI Agent架构与任务协议 | 定义大模型和ROS 2之间的受控协议 | Schema、白名单、状态机和测试桩通过 |
| AI Agent | M13 AI大模型层 | 完成任务理解、高层规划和多模态输入 | 结构化任务输出与异常拒绝达到指标 |
| AI Agent | M14 AI—ROS 2接口层 | 将结构化任务转换为机器人能力调用 | 合法性校验、语义映射、调用和反馈通过 |
| AI Agent | M15 AI仿真回归联调 | 先用测试桩，再接入已验收的仿真机器人 | 正常、异常、取消和超时场景通过 |
| AI Agent | M16 AI实体机器人联调 | 接入已验收的实际机器人 | 端到端综合任务及安全场景通过 |
| 发布阶段 | M17 整体稳定化与发布 | 完成AI机器人长稳、部署和文档 | 可重复部署、连续运行、可诊断和可回退 |

交付物：

- 环境自检报告；
- 工程目录；
- 依赖安装说明；
- 统一构建与测试命令；
- 首个Git基线版本。

### M1：资源、接口与测试基线

主要工作：

- 建立“对象—候选资源—仿真实现—实体实现—测试方法”矩阵；

## 9. 第一部分：ROS 2机器人开发规划

### 9.1 第一阶段：模拟机器人开发

在不依赖实体硬件和AI大模型的情况下，验证：

- 对象模型和软件包边界；
- 雷达、相机、IMU、底盘等独立要素；
- 运动、感知、定位、导航和安全子系统；
- 可由测试程序直接调用的ROS 2机器人能力接口；
- 完整机器人运行链；
- 自动测试、日志、复现和故障定位能力。

### 9.2 M2：仿真本体与底盘单元

工作顺序：

1. 建立URDF/Xacro模型和TF；
2. 接入成熟的差速控制资源；
3. 独立验证速度命令、轮速、里程计、转向和停车；
4. 验证命令超时停车、速度限制和生命周期；
5. 固化底盘接口契约测试。

验收：

- 前进、后退、原地转向和停车正确；
- `/cmd_vel`、`/odom`和TF方向一致；
- 模型无明显抖动、漂移异常和穿模；
- 自动测试可重复执行。

### 9.3 M3：仿真传感器单元

每类传感器必须单独启动、观察和测试，不能直接放入整机后只做目测。

| 对象 | 独立测试重点 |
|---|---|
| 激光雷达 | 扫描角度、距离、频率、噪声、时间戳、QoS、Frame |
| 相机 | 分辨率、帧率、编码、相机参数、时间戳、Frame |
| IMU | 角速度、加速度、方向、协方差、频率、Frame |
| 仿真编码器 | 左右轮方向、累计量、分辨率和里程计关系 |

每个对象形成：

- 独立启动文件；
- 默认参数；
- RViz2或诊断配置；
- 自动接口检查；
- rosbag测试样本；
- 通过/失败记录。

### 9.4 M4：运动与感知子系统集成

主要组合：

- 底盘＋编码器＋里程计＋TF；
- 编码器＋IMU＋`robot_localization`；
- 雷达＋TF＋障碍物数据链；
- 相机＋图像处理；
- 安全节点＋速度命令＋底盘。

重点验证多节点启动顺序、时间同步、QoS兼容、TF完整性、CPU占用、异常传播和安全停车。

### 9.5 M5：SLAM、定位与Nav2

按以下顺序集成成熟资源：

```text
雷达和里程计契约通过
→ SLAM建图
→ 地图保存和重载
→ AMCL或定位模式
→ Nav2全局规划
→ 局部控制和避障
→ 恢复行为和任务取消
```

验收场景至少包括：

- 固定路线多次到点；
- 静态障碍绕行；
- 临时障碍停车或重规划；
- 定位初始偏差；
- 导航取消；
- 传感器超时；
- 无法到达目标。

### 9.6 M6：仿真机器人综合验收

综合场景：

```text
测试程序下达机器人能力任务
→ ROS 2任务管理器校验
→ Nav2仿真导航
→ 到点执行感知
→ 返回任务状态和结果
```

此处使用明确的坐标、位姿或结构化机器人命令，不接入大模型。综合验收必须覆盖：

- 目标坐标越界或不可达；
- 导航失败或超时；
- 任务中途取消；
- 雷达、相机或定位数据中断；
- 安全节点触发；
- 多次重复执行及资源占用。

## 10. G1：仿真到实体准入门

只有全部满足以下条件，才进入实际机器人开发：

- 所有关键对象具有明确接口、配置和责任边界；
- 雷达、相机、IMU、底盘等仿真对象的独立测试通过；
- 运动、感知、定位、导航和安全子系统集成测试通过；
- 仿真整机可以稳定建图、定位、导航和避障；
- ROS 2机器人能力调用能够重复完成；
- 正常、异常、取消、超时和故障注入场景通过；
- 自动回归测试和日志能够定位到节点或子系统；
- 仿真与实体的统一接口已冻结；
- 实体硬件候选与ROS 2驱动兼容性已经完成书面审查；
- MCU、急停、通信失联和速度限制方案已经确定。

G1输出：

- 《仿真阶段测试报告》；
- 《实体接口冻结清单》；
- 《实体硬件与成熟资源选型表》；
- 《实体调试安全方案》；
- 是否准入实体阶段的明确结论。

## 11. 第二阶段：实际机器人开发

### 11.1 阶段目标

在保持上层接口不变的前提下，把仿真实现替换为实体实现，集中解决：

- 硬件通信和驱动；
- 设备安装和参数标定；
- 真实噪声、时延、丢包和漂移；
- 动力学差异和控制参数；
- 急停、失联停车和硬件安全；
- 真实环境的定位、导航、感知和长时间稳定性。

实体机器人仍不接入AI大模型，使用RViz2、ROS 2 CLI、测试程序或普通控制界面进行开发和验收。

### 11.2 M7：实体资源定型与安全准备

在采购或最终锁定硬件前完成：

- 底盘、MCU、电机驱动、编码器、雷达、相机和IMU选型；
- 驱动程序的ROS 2 Humble兼容性PoC；
- USB、Ethernet、串口和CAN拓扑设计；
- 电源、算力、带宽和安装空间核算；
- 急停、安全回路、保险和调试支撑方案；
- 实体参数、驱动版本及替代方案冻结。

### 11.3 M8：实体设备单元测试

实体设备仍按独立对象逐项测试：

```text
MCU协议离线测试
→ 电机架空测试
→ 编码器方向与计数测试
→ 底盘低速直线/旋转测试
→ 雷达独立测试
→ 相机独立测试
→ IMU独立测试
→ 急停和通信失联测试
```

每个实体对象应复用模拟阶段的接口契约测试；只新增实体特有的时延、丢包、温度、供电、标定和断连测试。

### 11.4 M9：实体运动与感知集成

主要工作：

- 底盘、编码器、里程计和TF闭环；
- 轮径、轮距、速度和转向标定；
- 编码器与IMU融合；
- 雷达和相机外参标定；
- 安全节点、急停和MCU保护联调；
- 手动/自动控制切换；
- rosbag和设备日志联合记录。

调试从架空、低速、限定区域逐步扩大，任何时候都保留人工急停。

### 11.5 M10：实体SLAM、定位与Nav2

原则上复用模拟阶段的软件包和接口，只调整：

- 实体TF和标定参数；
- 传感器噪声及协方差；
- 里程计和定位参数；
- 代价地图、膨胀半径和机器人轮廓；
- 规划器、控制器、速度和加速度限制。

若实体迁移迫使修改已冻结的公共能力接口，应暂停并检查是否发生架构泄漏。

测试除复用仿真阶段场景外，还要增加：

- 网络中断；
- MCU通信异常；
- 传感器物理断连；
- 电量不足；
- 定位漂移；
- 动态人员和障碍物；
- 人工急停及恢复。

### 11.6 M11：ROS 2机器人稳定化

交付：

- ROS 2机器人安装和部署脚本；
- 实体参数、地图和模型版本；
- 机器人操作、调试和维护手册；
- 节点、子系统和整机测试报告；
- 故障诊断与日志采集说明；
- ROS 2成熟资源、版本及许可证清单；
- ROS 2机器人基线标签和回退方案。

验收：

- 新环境可按文档重复部署；
- 自动测试和关键现场测试通过；
- 连续运行达到冻结指标；
- 故障可定位、关键服务可恢复；
- ROS 2机器人版本可回退；
- 不依赖AI Agent即可独立完成全部机器人能力验收。

## 12. G2：ROS 2机器人能力验收

G2是两部分规划之间的强制阶段门。只有全部满足以下条件，才启动AI Agent开发：

- 实体机器人能够独立完成建图、定位、导航、避障、感知和安全停车；
- 仿真与实体的公共能力接口一致；
- 机器人能力可通过Action、Service或受控Topic调用；
- 每项能力都有成功、失败、取消、超时和状态反馈定义；
- 雷达、相机、IMU、底盘、安全等关键对象均有独立测试；
- 子系统、整机、实体安全和长稳测试通过；
- 能力接口、消息Schema、QoS、TF和错误码已冻结；
- 仿真测试环境和实体测试环境均可重复部署；
- ROS 2机器人问题清单中不存在阻止AI接入的严重缺陷。

G2输出：

- 《ROS 2机器人能力清单》；
- 《ROS 2机器人综合验收报告》；
- 《AI调用接口冻结说明》；
- 《仿真与实体回归测试集》；
- 是否准入AI Agent开发的明确结论。

## 13. 第二部分：AI Agent开发规划

### 13.1 阶段目标

在不改变ROS 2机器人内部实现的前提下，建立：

- AI大模型层：理解文字、语音、图片和视频，完成任务理解与高层规划；
- AI—ROS 2接口层：结构化任务、语义目标物理化、合法性校验、能力调用和结果反馈；
- 受约束的任务状态机、能力白名单和安全边界；
- 测试桩、仿真机器人、实体机器人三级联调与回归体系。

### 13.2 M12：AI Agent架构与任务协议

主要工作：

- 定义结构化任务Schema、字段、版本和错误码；
- 将G2能力清单转换为AI可调用工具白名单；
- 定义任务状态机、取消、超时、重试和结果反馈；
- 建立语义地点、物理位姿和目标对象的数据模型；
- 建立模拟Nav2、模拟感知和模拟状态接口；
- 为合法、非法、歧义和越权任务建立测试样本。

验收重点是协议和安全边界，不要求大模型已经达到最终效果。

### 13.3 M13：AI大模型层

主要工作：

- 选择本地或云端大模型及多模态方案；
- 设计系统提示词、工具描述和结构化输出约束；
- 实现任务理解、必要澄清和高层步骤规划；
- 对无效、歧义、危险或能力范围外的请求进行拒绝或澄清；
- 建立离线任务样本集和自动评测。

大模型只输出高层结构化任务，不直接发布`/cmd_vel`，也不绕过AI—ROS 2接口层调用底盘。

### 13.4 M14：AI—ROS 2接口层

主要工作：

- 校验大模型输出Schema、类型、范围和权限；
- 将语义地点映射为经过确认的地图位姿；
- 将结构化任务适配为ROS 2 Topic、Service或Action调用；
- 汇总执行进度、成功、失败、取消和超时结果；
- 对机器人状态、定位状态和安全状态进行前置检查；
- 形成完整审计日志和任务关联ID。

本层不得替代Nav2规划、底盘控制器或硬件安全。

### 13.5 M15：AI仿真回归联调

按以下顺序逐级替换：

```text
固定结构化任务
→ 测试桩
→ G2冻结的仿真机器人能力
→ 完整AI Agent仿真任务
```

综合场景：

```text
用户：“去客厅门口看看有没有人”
→ AI大模型生成结构化任务
→ AI—ROS 2接口校验并查询语义地点
→ 调用仿真Nav2导航
→ 调用仿真人员检测
→ 返回执行结果
```

必须覆盖地点不存在、目标不可达、导航失败、感知超时、任务取消、机器人忙碌、安全状态异常和大模型输出不合规等场景。

### 13.6 M16：AI实体机器人联调

在保持AI任务协议不变的情况下，将调用目标从仿真机器人切换为G2验收通过的实体机器人。复用M15测试集，并增加：

- 网络和模型服务中断；
- 实体定位漂移；
- MCU或传感器异常；
- 电量不足；
- 动态人员和障碍物；
- 人工急停及恢复；
- AI任务与人工控制冲突。

发现问题时，先判断属于AI理解、AI—ROS 2适配、ROS 2能力接口还是实体硬件，不允许用跨层临时补丁掩盖责任边界。

### 13.7 M17：整体稳定化与发布

交付：

- AI机器人整体安装和部署脚本；
- 提示词、任务Schema、地图、参数和模型版本；
- 操作、调试、维护和安全手册；
- 全部测试报告和已知问题清单；
- 第三方资源、模型及许可证清单；
- 整体发布标签和回退方案。

验收：

- 新环境可以按文档重复部署；
- ROS 2机器人脱离AI后仍可独立运行；
- AI Agent只能调用白名单能力；
- 正常、异常、取消、超时和安全场景通过；
- 综合任务可重复完成；
- 系统连续运行达到冻结指标；
- 故障可定位到明确层级，发布版本可回退。

## 15. VS Code + Codex（或Claude）研发方式

### 15.1 工具定位

- VS Code：代码、配置、终端、调试和Git入口；
- Codex：主工程代理，负责实现、运行测试、分析故障和维护文档；
- Claude：可用于设计复核、代码审查和第二意见；
- ROS 2、Gazebo、测试程序和实体日志：提供客观验收证据；
- Git：保存检查点、支持审查和回退。

AI编程工具不属于机器人运行时，不在线直接控制实体机器人。

### 15.2 每个模块的开发循环

```text
明确对象职责和验收
→ 检索并评估成熟资源
→ 建立最小可运行样例
→ 冻结接口契约
→ 实现配置、适配或自研增量
→ 单元/节点测试
→ 子系统集成测试
→ 场景测试
→ 保存Git检查点和测试证据
```

### 15.3 AI编程代理规则

`AGENTS.md`至少规定：

- 当前阶段、里程碑和验收标准；
- 包、节点、接口、QoS、TF和参数规范；
- 仿真/实体统一接口及禁止泄漏规则；
- 成熟资源优先和禁止无依据重写规则；
- 改动前必须检查现有实现；
- 改动后必须执行的构建和测试；
- 不得删除或降低既有测试来掩盖失败；
- 实体操作的限速、急停和人工确认要求；
- 同一路线反复失败时暂停并重新评估架构；
- 未经确认不得重构已经稳定通过验收的模块。

建议始终只指定一个主执行代理。若使用另一AI审查，应先形成Git检查点，审查意见经用户确认后再由主代理增量修改。

## 16. 质量指标与验收证据

M1建立指标模板，M5前冻结机器人仿真阈值，M7硬件确定后冻结实体阈值，M12建立AI Agent指标，M15前冻结AI端到端阈值。至少记录：

- 构建和自动测试通过率；
- 节点启动、停止和重启结果；
- Topic频率、时延、丢包、时间戳和QoS；
- TF完整性和更新频率；
- 导航到达率、位置误差和耗时；
- 碰撞次数和最小障碍距离；
- 定位丢失次数和恢复时间；
- 急停、失联和命令超时停车时间；
- AI任务解析正确率和非法任务拦截率；
- 端到端任务成功率、耗时和失败原因；
- 连续运行时间、资源占用和故障恢复情况。

每个里程碑必须留下：

- 自动测试报告；
- 关键日志或rosbag；
- 参数与软件版本；
- 人工验收记录；
- 已知问题和限制；
- 对应Git提交或标签。

## 18. 主要风险与控制

| 风险 | 控制措施 |
|---|---|
| 把“有成熟包”误认为“安装即可使用” | 资源卡、最小PoC、接口契约和集成测试 |
| 一开始同时开发所有模块 | 按对象、子系统和里程碑逐层增加能力 |
| 仿真接口与实体接口不一致 | M1定义公共接口，G1正式冻结 |
| 只做整机演示，不做独立测试 | 每个对象必须通过完成定义后才能集成 |
| 只做自底向上，过晚发现机器人能力接口问题 | 模拟阶段从验收场景反推接口，并在G2前冻结 |
| 第三方包升级破坏系统 | 锁定版本、保存配置、建立自动回归和回退方式 |
| 过早接入大模型 | G2通过后才启动AI Agent开发 |
| 大模型直接控制底盘 | Schema、能力白名单、安全节点和MCU保护 |
| 实体调试造成伤害或损坏 | 架空、低速、限定区域、人工急停和检查清单 |
| Codex反复局部修补 | 连续失败触发架构复盘，禁止降低验收标准 |
| 多AI同时改同一工作区 | 单一主代理、Git检查点、审查与执行分离 |

## 19. 项目启动顺序

当前只启动M0，不立即接入大模型，也不立即开展实体运动测试：

1. 检查Ubuntu 22.04、ROS 2 Humble、磁盘、网络和代理；
2. 验证示例节点、`colcon`、RViz2和Gazebo；
3. 建立`ai_robot_ws`、Git和工程目录；
4. 建立`README.md`、`AGENTS.md`和架构基线；
5. 建立环境自检、构建和测试入口；
6. 创建最小C++节点、Python节点及单元测试；
7. 建立首批资源卡模板；
8. 形成《M0验收记录》；
9. M0通过后进入M1的资源调研、接口和测试基线工作。

## 20. 项目完成判定

只有同时满足以下条件，项目才算完成：

- ROS 2机器人模拟阶段、实际机器人阶段和AI Agent阶段均通过各自综合验收；
- ROS 2机器人通过G2后才开始AI Agent开发；
- 仿真与实体使用相同的上层任务和ROS 2能力接口；
- 每个关键对象可独立启动、测试、替换和诊断；
- 成熟资源的来源、版本、许可证、配置和测试均可追踪；
- 单元、节点、契约、集成、系统和端到端测试形成自动回归；
- 机器人能够稳定建图、定位、导航、避障和感知；
- 硬件急停、通信失联停车和速度限制有效；
- AI只能通过受约束的能力接口调用ROS 2；
- 综合场景能够重复完成，而不是偶然演示成功；
- 环境、代码、配置、测试和操作文档可以复现；
- 发布版本可诊断、可维护、可扩展并可回退。
